# 2D2 — аналитический кабинет абонента

Готовый исходный код frontend-приложения на **React 18 + JavaScript + Vite 6** по теме курсового проекта: «Разработка аналитического приложения подключения и мониторинга услуг телекоммуникационного оператора».

Интерфейс ориентирован на шесть переданных изображений: белая верхняя навигация, серый фон кабинета, бирюзовые акценты, карточная компоновка, каталог подключённых/доступных услуг, финансовая сводка, счета и аналитическая панель. Вариант для небольших экранов адаптирован отдельно. Декоративные фрагменты логотипа и иллюстрации входа получены из предоставленных макетов.

**Важно:** в приложении **нет подмены ответов backend статическими демонстрационными данными**. После входа всё содержимое кабинета, включая значения на графиках, загружается из API. Для функционирования необходим запущенный backend, реализующий `docs/API_endpoints.md`. Backend и PostgreSQL не входят в этот архив.

## Запуск

Потребуется Node.js **20.19+ или 22.12+** и npm.

```bash
cd 2d2-frontend
npm install
cp .env.example .env
npm run dev
```

Откройте адрес из вывода Vite (обычно `http://localhost:5173`). По умолчанию клиент обращается к относительному адресу `/api/v1`, а dev-сервер Vite пересылает `/api/*` на `http://localhost:5555`. Убедитесь, что backend запущен на порту `5555`.

Если backend находится на другом хосте или порту, измените `VITE_BACKEND_PROXY` в `.env`:

```dotenv
VITE_API_URL=
VITE_BACKEND_PROXY=http://localhost:5555
```

Либо задайте полный URL API (он должен заканчиваться на `/api/v1`):

```dotenv
VITE_API_URL=https://your-backend.example/api/v1
```

При использовании `VITE_API_URL` браузер обращается к этому домену напрямую — **backend должен разрешить CORS** для origin frontend. Перезапустите Vite после изменения `.env`.

### Сборка

```bash
npm run build
npm run preview
```

Содержимое `dist/` можно разместить на статическом хостинге. Для размещения на одном домене с API настройте reverse proxy маршрута `/api/v1` на backend, а все остальные пути SPA направляйте на `index.html` (history fallback). Для отдельного API-домена установите `VITE_API_URL` **до** сборки.

## Архитектура

```text
2d2-frontend/
├── src/
│   ├── main.jsx                    # React, Router, QueryClient, Provider'ы
│   ├── App.jsx                     # Защищённые маршруты
│   ├── styles.css                  # Визуальные стили и responsive layout
│   ├── lib/
│   │   ├── api.js                  # Fetch, Bearer JWT, refresh, каталог endpoints
│   │   └── format.js               # Валюта BYN, даты Minsk, трафик, валидация
│   ├── auth/AuthProvider.jsx       # Текущая сессия, вход/регистрация/выход
│   ├── components/
│   │   ├── Shell.jsx               # Навигация и значки уведомлений
│   │   └── UI.jsx                  # Карточки, модальные окна, состояния, toast
│   ├── pages/
│   │   ├── AuthPages.jsx           # Логин/пароль, SMS-вход, регистрация
│   │   ├── Dashboard.jsx           # Баланс, остатки, тариф, рекомендации
│   │   ├── Services.jsx            # Поиск и управление услугами
│   │   ├── TariffsNumberProfile.jsx# Тарифы, номер, профиль
│   │   ├── Finance.jsx             # Финансы и оплата
│   │   ├── Analytics.jsx           # Графики, контакты, календарь
│   │   └── Notifications.jsx       # Уведомления и прочтение
│   └── assets/                     # Графика из предоставленных макетов
├── docs/API_endpoints.md           # Исходный REST API-контракт
├── scripts/check-api-contract.cjs # Офлайн-аудит 28 browser endpoints
└── vite.config.js                  # Proxy до backend
```

Серверные данные кэшируются через TanStack React Query. После изменения услуг, тарифов, контактов или статусов уведомлений соответствующие query автоматически инвалидируются. Ошибки API показываются в интерфейсе, запросы выполняются с индикаторами загрузки, POST/PUT/PATCH не повторяются автоматически. Вкладки услуг и фильтры уведомлений синхронизированы с URL.

## Маршруты приложения

| URL | Что делает |
|---|---|
| `/login` | Вход по логину и паролю либо SMS-коду |
| `/register` | Регистрация после SMS-подтверждения номера |
| `/` | Главная: баланс, тариф, подключённые услуги, остатки, рекомендации |
| `/services` | Подключённые/доступные услуги, категории, поиск, включение и отключение |
| `/tariffs` | Список тарифов и смена тарифного плана |
| `/number` | Название и блокировка/разблокировка номера |
| `/profile` | Данные пользователя и лицевого счёта |
| `/finance` | Карточки финансового раздела |
| `/finance/charges` | Начисления по месяцам |
| `/finance/invoices` | Счета за период |
| `/finance/invoices/:id` | Позиции конкретного счёта |
| `/finance/payments` | История пополнений и их статусы |
| `/finance/details` | Детализация звонков/трафика с фильтрами дат и постраничной навигацией |
| `/finance/topup` | Создание платёжной сессии с idempotency key |
| `/analytics` | Звонки, начисления, популярные услуги, дневной трафик, календарь, избранные контакты |
| `/notifications` | Сообщения и предупреждения, отметка прочитанного |

## Покрытие REST API

Клиент реализует **28 из 29** методов из исходного контракта, а именно:

| Категория | HTTP-методы |
|---|---|
| Авторизация | `POST /auth/otp/request`, `POST /auth/register`, `POST /auth/login`, `POST /auth/otp/verify`, `POST /auth/refresh`, `POST /auth/logout` |
| Абонент | `GET /me`, `PATCH /me`, `PATCH /number`, `GET /dashboard` |
| Тарифы и услуги | `GET /tariffs`, `PUT /number/tariff`, `GET /services`, `PUT /services/{id}/connection` |
| Финансы | `GET /finance/summary`, `GET /finance/charges`, `GET /finance/invoices`, `GET /finance/invoices/{id}`, `GET /finance/payments`, `GET /finance/usage-details`, `POST /finance/topups` |
| Аналитика | `GET /analytics` |
| Избранные | `GET /favorites`, `POST /favorites`, `PATCH /favorites/{id}`, `DELETE /favorites/{id}` |
| Уведомления | `GET /notifications`, `PATCH /notifications/{id}/read` |

**29-й метод `POST /integrations/payment-webhook` браузер вызывать не должен.** По условиям API он предназначен **только для подписанных запросов платёжного провайдера к backend**. Запрос `POST /finance/topups` создаёт pending-платёж и перенаправляет на `checkout_url`. Баланс изменяет только backend после проверенного webhook; интерфейс не симулирует успешную оплату.

### Особенности авторизации и платежей

- Access-токен добавляется как `Authorization: Bearer <access_token>` во все закрытые запросы.
- При `401` автоматически делается один запрос обновления токенов по `POST /auth/refresh`, затем исходный запрос повторяется. Одновременные запросы на refresh объединяются.
- Refresh-токен ротируется согласно контракту; при отказе авторизации локальная сессия сбрасывается.
- В учебном frontend оба токена лежат в **sessionStorage** текущей вкладки, а не в localStorage. Для боевой эксплуатации рекомендуется согласовать с backend использование защищённой `HttpOnly; Secure; SameSite` cookie-сессии, CSP и защиту от XSS.
- SMS-код не сохраняется, не логируется и никогда не показывается в «успешном» ответе без фактического ответа backend.
- У платёжного запроса есть заголовок `Idempotency-Key` с `crypto.randomUUID()`; один и тот же ключ используется при повторной попытке на ту же сумму в рамках открытой формы.
- Для всех денежных значений используется BYN, отображение — два знака после запятой. В HTTP отправляются строки, а не округлённые суммы числом.
- Для графиков принимаются **реальные значения** `minutes_by_month`, `payment_distribution`, `internet_by_day`, `popular_services`, `calendar_activity_days` из `/analytics`. `payment_distribution` отражает начисления, а не поступления из банка.

## Проверки

Офлайн-аудит путей API и smoke-тест вызовов всех 28 методов (включая авторизацию, refresh и idempotency key) — без сторонних зависимостей:

```bash
npm run check:api
npm run smoke:api
```

Unit-тесты форматирования (после `npm install`):

```bash
npm test
```

Проверка сборки после установки зависимостей:

```bash
npm run build
```

**Ограничение подготовки архива:** в среде генерации не было доступа к `registry.npmjs.org`, поэтому `npm install`, реальная Vite-сборка и интеграционные HTTP-запросы к вашему backend не были выполнены. Исходные JSX/JS-модули отдельно проверены парсером TypeScript без синтаксических ошибок; офлайн-аудит контрактов и smoke-тест API-клиента с имитацией HTTP-ответов пройдены. Это исходный проект, готовый к установке стандартной командой `npm install`, а не готовый production-бандл.

Для полноценной интеграционной проверки запустите backend на `localhost:5555`, выполните регистрацию с учебным mock-SMS backend либо войдите под реальным пользователем и проверьте сценарии: вход, смена тарифа, подключение/отключение услуг, чтение аналитики, пополнение через настроенного платёжного провайдера.
